# 动能回流高质量信号双通道警报设计

日期：2026-08-01  
状态：已确认，待实施计划

## 目标

当动能回流扫描产生新的有效高质量信号时，同时提供：

1. 企业微信群机器人消息；
2. AXIOM 网页打开期间的“金币落袋三音”提醒。

提醒只报告扫描事实，不构成交易建议，不改变扫描、交易策略、持仓、订单或交易记录。

## 已确认规则

- 仅提醒`quality_label=HIGH`且`status=ACTIVE`的信号。
- 首次启用只以当前高质量信号建立基线，不补发历史提醒。
- 同一`signal_key`只提醒一次。
- 信号最初不是高质量、后续首次升级为高质量时提醒一次。
- 后续价格、评分、窗口或状态更新不重复提醒。
- 自动扫描与手动扫描使用相同规则和同一去重账本。
- 浏览器声音在任意 AXIOM 页面生效，不要求停留在动能回流菜单。
- 企业微信和浏览器声音为独立通道；一个通道失败不影响另一个。

## 方案选择

采用服务端统一判定方案。扫描结果合并成功后，由服务端根据持久化警报账本判定是否产生新警报；企业微信由服务端发送，浏览器只读取脱敏后的警报事件。

未采用以下方案：

- 浏览器直接判定并调用 Webhook：页面关闭即失效，且会泄露 Webhook。
- 独立 systemd 通知服务：隔离性较好，但当前规模会增加无必要的部署和监控成本。

## 组件边界

### 1. 警报领域模块

新增独立模块，负责：

- 校验和加载警报配置；
- 从扫描结果中选择`HIGH + ACTIVE`行；
- 根据`signal_key`和历史状态识别首次进入高质量；
- 原子读写警报账本；
- 生成稳定递增的`alert_id`；
- 格式化企业微信 Markdown；
- 调用企业微信 Webhook并记录通道状态。

该模块不导入或调用任何下单逻辑。

### 2. 警报配置

使用独立服务器配置文件，不混入交易配置。字段包括：

- `wechat_enabled`；
- `wechat_webhook`；
- 最近测试发送结果；
- 最近正式发送结果与错误摘要。

Webhook 以明文凭证形式仅保存在服务器，文件权限限制为服务账户可读。普通交易页面永远不返回该字段；管理接口只返回是否已配置和固定掩码，空值保存不得覆盖现有 Webhook。

### 3. 警报账本

使用独立、版本化、原子替换的 JSON 账本，至少保存：

- 已观察信号及其是否曾进入高质量；
- `alert_id`、`signal_key`和首次高质量时间；
- 警报事实快照；
- 企业微信`pending / delivered / failed`状态；
- 尝试次数、最后尝试时间和脱敏错误；
- 当前企业微信通道投递游标。

账本不保存完整 Webhook。重启时继续使用该账本去重和恢复待发送事件。

### 4. 单进程通知工作器

复用`macd-bot`进程，使用单个守护工作器串行发送企业微信消息，不新增 systemd 服务。扫描线程只完成警报判定、持久化和入队，不等待外部网络请求。

工作器启动时加载待发送事件；发送设置短超时和有限重试。成功后持久化`delivered`。明确失败后保留`failed/pending`状态，由后续调度按退避时间重试，不阻塞下一次扫描。

企业微信 Webhook 不提供端到端幂等键。服务器在收到成功回执后不会重复发送；网络超时造成“对方已收到但本地未收到回执”时仍存在极低概率重复，管理页面应明确展示这一边界。

## 数据流

1. 自动或手动扫描完成并成功合并历史。
2. 警报模块读取本次完整结果。
3. 首次运行时，把当前`HIGH + ACTIVE`集合写为基线，不生成事件。
4. 后续发现新`signal_key`首次达到`HIGH + ACTIVE`时，先原子写入警报事件。
5. 企业微信已启用时，将事件交给通知工作器。
6. 浏览器通过只读警报接口取得比自身游标更新的事件。
7. 两个通道分别更新自己的投递或已读游标，不改变信号历史。

企业微信从关闭切换为开启时，将当前最新`alert_id`设为通道基线，不补发开启前事件。每台浏览器首次开启声音时也将当前最新`alert_id`设为本地基线。

## 企业微信消息

使用简洁 Markdown，示例：

```text
【AXIOM 高质量回流警报】

TRXUSDT · SHORT
触发：新信号 / 升级为高质量
价格：0.32688
EMA50：0.326913
日线：看跌吞没
窗口：1/5
量比：2.3x
首次发现：2026-08-01 16:20 北京时间
```

消息字段来自事件生成时的不可变快照，不在重试时用当前行情重算。

## 管理后台

在动能回流设置中增加：

- 企业微信提醒开关；
- Webhook 输入框及已配置掩码；
- 发送测试消息按钮；
- 最近一次测试状态；
- 最近一次正式发送时间、状态和脱敏错误。

保存行为遵循现有空凭证不覆盖规则。测试发送不创建正式警报事件，也不推进投递游标。

## 浏览器声音

- 使用 Web Audio API 实时合成约1秒的“金币落袋三音”。
- 三个短促金属音依次升高，并带快速衰减；不复制任何品牌原始提示音。
- 页面提供“开启/关闭声音”和“测试声音”按钮。
- 浏览器首次必须通过用户点击创建或恢复`AudioContext`。
- 开关及最后播放的`alert_id`保存在当前浏览器本地存储中。
- 全站使用轻量警报轮询；只有网页保持打开且声音已授权时播放。
- 新打开网页或首次开启声音时只建立当前游标基线，不播放旧警报。
- 一次轮询收到多个新事件时只播放一轮声音，并将游标推进到最大`alert_id`，避免声音连发。

## API与安全

新增接口分为两类：

- 普通已登录页面：只读取得最新警报游标和游标后的脱敏事件；不包含 Webhook 或内部错误详情。
- 管理员接口：读取掩码状态、保存开关/Webhook、发送测试消息。

所有管理写接口继续使用现有管理员认证。Webhook 必须在日志、异常、响应和测试输出中脱敏。前端源码、HTML、浏览器网络响应和警报账本不得出现完整 Webhook。

## 错误处理

- 配置缺失或无效：企业微信通道标记不可用，浏览器声音继续工作。
- 扫描失败：不生成警报，不改变通道游标。
- 警报账本损坏：停止发送并在管理后台显示错误，不根据空账本重新群发。
- Webhook 返回业务错误：记录脱敏错误，按退避规则有限重试。
- 服务重启：恢复账本和待发送状态，不重新提醒已成功事件。
- 浏览器自动播放被阻止：显示“需要点击恢复声音”，不影响微信发送。

## 测试与验收

### 服务端

- 首次初始化只建立基线。
- 新`HIGH + ACTIVE`信号生成一个事件。
- 标准信号升级为高质量生成一个事件。
- 非活动、高质量以下、重复扫描和后续字段变化不生成事件。
- 自动与手动扫描交叉执行仍只生成一次。
- 重启后不重复，待发送事件可恢复。
- Webhook成功、超时、业务失败、退避重试和最终成功均可验证。
- 损坏账本失败关闭，不触发群发。
- Webhook空值不覆盖、响应掩码、日志脱敏和权限保护均有测试。

### 浏览器

- 第一次开启声音不播放现有事件。
- 任意 AXIOM 菜单打开时，新事件播放一次金币落袋三音。
- 页面轮询、菜单切换和刷新不重复播放。
- 多事件批次只播放一轮并推进到最大游标。
- 关闭声音后不播放；测试声音不改变正式事件游标。
- 自动播放被阻止时显示恢复提示。

### 回归与部署

- 完整单元测试、Python编译和补丁检查通过。
- 服务器先备份代码、警报配置/账本及现有受保护状态文件。
- 仅部署批准的通知、页面和管理后台文件。
- 验证服务状态、接口、测试微信消息、页面声音按钮、日志错误和受保护交易数据。
- 部署后更新本地`PROGRESS.md`，记录备份、部署文件、哈希和验收结果。

## 非目标

- 不向个人微信模拟登录或绕过企业微信官方接口。
- 不增加短信、邮件、电话或其他通知渠道。
- 不提供交易建议或自动下单入口。
- 不对历史信号补发警报。
- 不为每个普通用户配置独立 Webhook；首版使用管理员维护的单一企业微信群机器人。
