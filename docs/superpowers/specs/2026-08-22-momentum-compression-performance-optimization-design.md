# 动能压缩扫描性能优化设计

## 1. 背景

生产环境的 15 分钟动能压缩扫描已启用，但全市场扫描无法在一个 15 分钟周期内完成。2026-08-22 的现场检查显示，一轮扫描从北京时间 14:15 开始，超过 1 小时仍未完成，状态接口显示 `structure_scanning=true`、`scan_overdue=true`，且本轮报告尚未生成。

瓶颈位于最大连续结构后缀计算。现有实现对每个交易对的 LONG、SHORT 两个方向分别遍历候选后缀，并在每个候选后缀内重复执行数据切片、枢轴识别、线性拟合、边界触碰、EMA 顺序、摆动结构和收缩率计算。生产服务器只有 2 个 CPU 核，线程池不能有效并行这些 Python CPU 密集型计算。

## 2. 目标与非目标

### 2.1 目标

- 对约 500 个 USDT 永续交易对完成一轮全市场扫描，生产验收时间不超过 5 分钟。
- 保持相同输入、参数和评估时间下的策略结果等价。
- 保留最大连续结构后缀的原始定义：先选择满足全部非 G01 条件的最大连续结构后缀，再应用 `15 <= bars(W) <= 100` 长度门槛。
- 保持公共函数、状态字段、拒绝代码、观察池、事件和警报数据格式兼容。
- 避免增加交易主循环的 CPU 争用和生产运维复杂度。

### 2.2 非目标

- 不调整任何课程硬规则、参数阈值、评分权重或突破判定。
- 不把候选窗口静默截断为最近 100 根。
- 不引入跨轮持久化计算缓存。
- 本阶段不把计算迁移到多进程；只有算法等价优化仍无法达到目标时，才另行设计并审批并行计算方案。

## 3. 约束与等价性定义

对相同的 OHLCV、`live_price`、`evaluated_at_ms`、高周期方向和 `CompressionParams`，优化前后必须保持以下结果一致：

- LONG、SHORT 返回顺序；
- `state` 与 `rejection_reasons`；
- `compression_bars`、起止时间和 `compression_id`；
- 上下边界、斜率、ATR、EMA、EMA 距离和收缩率；
- 枢轴数量、方向触碰数量与触碰时间；
- 摆动结构、质量评分和评分分项；
- 窗口过短、窗口过长、没有有效结构后缀及异常输入的审计结果。

浮点字段使用现有 NumPy/Pandas 计算精度进行比较；不得通过放宽业务阈值来制造等价。

## 4. 方案

采用算法等价优化，不依赖新增进程。

### 4.1 单次准备输入

`evaluate_both_sides` 对输入数据只执行一次：

1. 必填列和有限数校验；
2. 未收盘 15 分钟 K 线过滤；
3. 数值类型转换；
4. EMA8、EMA21 和 ATR14 计算；
5. 将后续热点字段转换为只读 NumPy 数组。

LONG、SHORT 共享准备结果。单方向 `evaluate_side` 继续保持现有行为和返回格式。

### 4.2 精确候选起点剪枝

EMA 方向和收盘价位于 EMA 区域之外是全窗口硬条件。对于固定终点，只要候选后缀仍包含最后一个违反这些条件的 K 线，该候选必然失败。因此每个方向可以直接从最后一个相关违规位置之后开始寻找，而不逐一计算这些必然失败的更长后缀。

最后一根 K 线的 EMA 距离条件与候选起点无关。如果该条件失败，则所有候选后缀都会失败，可以直接返回与原算法相同的全窗口拒绝结果。

这些剪枝只跳过可由硬条件证明必然失败的候选，不改变第一个有效候选的位置。

### 4.3 共用方向无关计算

对同一候选起点，以下计算与 LONG/SHORT 无关，只计算一次：

- 枢轴高点与低点；
- 上下 `pivot-envelope`；
- 上下边界宽度与收缩率。

方向相关的 EMA 条件、触碰边界和摆动结构在共享结果上分别计算。每个方向仍独立选择自己的第一个有效候选，因此保持各自最大连续结构后缀语义。

### 4.4 NumPy 热点实现

候选循环内部避免反复创建 DataFrame、重置索引、拼接 Series。枢轴、EMA 条件、触碰 run、摆动结构和宽度计算使用 NumPy 数组；线性拟合继续保持与现有 `np.polyfit` 相同的输入和语义。

只有在最终选定窗口或生成审计结果时构造 Pandas 视图和现有指标字典，保持外部接口不变。

## 5. 数据流与失败处理

扫描服务的交易对获取、成交额过滤、K线请求、价格快照和结果写入流程保持不变。优化仅位于纯计算模块。

单个交易对计算异常继续由现有扫描服务记录为错误，不终止全市场扫描。不得吞掉异常或把计算失败计为正常 `eligible=0`。

扫描状态只有在一轮真实结束后才更新 `scanned`、`eligible`、`errors` 和耗时。生产验收时，`eligible=0` 只有在 `scanned` 已覆盖本轮实际交易对且扫描已结束时才是有效市场结论。

## 6. 测试设计

### 6.1 测试驱动顺序

1. 先增加会在旧实现上失败的性能结构测试，例如双方向不得重复准备指标、可证明无效的候选不得进入完整包络计算。
2. 保留旧算法作为测试侧参考函数，不进入生产代码。
3. 使用固定边界样本和固定随机种子样本比较参考结果与优化结果。
4. 先观察新增测试按预期失败，再实现最小优化使其通过。

### 6.2 等价性覆盖

- LONG 与 SHORT 有效结构；
- EMA 方向违规位于窗口头部、中部和尾部；
- 收盘价进入 EMA 区域；
- EMA 距离过宽；
- 枢轴不足；
- 触碰不足或连续触碰去重；
- 摆动结构失败；
- 收缩率失败；
- 14、15、100、101 根边界；
- 没有任何有效结构后缀；
- 未收盘尾部 K 线、非有限数据和异常参数输入。

### 6.3 性能验证

- 本地记录 220 根 K 线单币双方向计算的优化前后中位耗时，使用同一数据与重复次数。
- 用约 500 份输入进行离线批量基准，确认纯计算预算能够支撑 5 分钟目标。
- 性能测试不能以降低规则覆盖、缩短输入长度或跳过方向为代价。

## 7. 部署与生产验收

1. 本地运行相关测试、全量测试、Python 编译检查和 `git diff --check`。
2. 部署前在服务器创建带时间戳备份。
3. 仅上传本次必要的本地已提交文件。
4. 重启 `macd-bot`，不修改现有持仓、订单或用户配置。
5. 检查服务状态和错误日志。
6. 等待一轮真实全市场扫描结束，并验证：
   - 总耗时不超过 5 分钟；
   - `structure_scanning=false` 且 `scan_overdue=false`；
   - `scanned` 覆盖实际合格交易对数量；
   - `errors` 有明确数量和日志，不得伪装为零合格结果；
   - 观察池、事件和警报仍按原格式更新。
7. 部署验证后更新本地 `PROGRESS.md`，记录代码变更、部署文件、服务器备份和验证结果。

## 8. 回滚

如果等价性测试失败、生产扫描超过 5 分钟、交易主循环出现异常，或状态数据不完整，则立即恢复部署前备份中的扫描模块并重启 `macd-bot`。回滚只恢复本次代码文件，不覆盖数据库、持仓状态、事件文件或用户配置。
