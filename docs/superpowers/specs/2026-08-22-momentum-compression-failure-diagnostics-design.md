# 动能压缩扫描失败诊断与交易对显示修复设计

日期：2026-08-22

## 问题与边界

线上观察池中的 `OUSDT` 在页面被移除 `USDT` 后缀，只显示为 `O`，容易被误认为数字 `0` 或空交易对。同时，扫描状态只保存“13 symbol scan failures”这类汇总；单币异常在并发任务边界被吞掉，扫描完成后无法确认失败交易对和原因。

本修复不改变动能压缩选币规则、成交额门槛、候选池状态机、突破判定、声音提醒、企业微信投递或交易逻辑。

## 方案

### 交易对显示

- 观察池和突破列表展示完整交易对，例如 `OUSDT`，不再移除 `USDT` 后缀。
- 继续使用现有 HTML 转义，避免交易对字段形成可执行标记。

### 可诊断的 K 线请求

- 为共享 `fetch_klines()` 增加默认关闭的异常透传参数；现有调用保持吞错并返回 `None` 的兼容行为。
- 只有动能压缩结构扫描开启异常透传，以取得 HTTP 状态、超时或连接异常的真实原因。
- 单币 15 分钟 K 线第一次请求失败后重试一次。第二次成功即按正常结果处理，不增加错误数。
- 两次均失败才将该交易对计入本轮错误。高周期确认仍沿用现有行为，不扩大本次修复范围。
- 全量价格快照中缺失的交易对不发起无意义的 K 线扫描，直接记录为“实时价格缺失”。

### 状态持久化与接口

- 状态文件新增 `last_scan_failures`，只保存最近一轮最终失败项，不累积历史。
- 每个失败项包含 `symbol`、`stage`、`error_type`、`message` 和 `attempts`。
- 异常消息转换为单行并截断，避免状态文件膨胀或页面泄露无关上下文。
- 扫描报告和用户状态接口返回同一份失败明细；汇总错误数必须等于明细数量。
- 扫描没有最终失败时写入空数组，并清空汇总错误文本。

### 页面呈现

- 状态卡继续显示错误总数。
- 状态卡下方增加“扫描失败明细”区域，按交易对展示阶段、异常类型、原因和尝试次数。
- 没有失败时隐藏该区域；所有文本使用现有转义函数。

## 数据流

1. 扫描器取得交易对全集和实时价格快照。
2. 每个有价格的交易对执行最多两次 15 分钟 K 线请求。
3. 成功结果进入策略评估；最终失败结果进入结构化失败列表。
4. 扫描事务同时保存候选池、错误汇总和最近失败明细。
5. 状态接口读取持久化明细，前端显示完整交易对和失败详情。

## 测试与验收

- 测试共享 K 线函数默认行为保持兼容，启用异常透传时保留真实异常。
- 测试第一次失败、第二次成功时不计错；连续两次失败时只生成一条结构化失败记录。
- 测试实时价格缺失产生明确失败原因。
- 测试状态文件仅保留最近一轮失败并能兼容旧状态文件。
- 测试状态接口返回失败明细，页面显示完整 `OUSDT` 且转义错误文本。
- 运行相关单测、完整测试集和 Python 编译检查；如部署，先备份服务器，只重启受影响服务并更新本地 `PROGRESS.md`。
